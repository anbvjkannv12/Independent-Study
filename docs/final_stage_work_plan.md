## 工作 1：保存與備份（最先做）

### 1.1 為什麼最先做

- `git remote -v` 顯示這個 repo **沒有任何遠端**，程式碼和文件只存在這台電腦上。
- `.gitignore` 排除了 `data/`（約 1.8 GB）、`logs/`（約 142 MB）與 `models/live/`。所有實驗的逐列預測、結果 JSON、凍結模型都**不在 git 裡**。
- 有些結果只存在 worktree 裡，main 沒有副本。例如總報告第八節寫明，特徵消融 v2 的 logs 只放在 `C:/Users/user/orca/workspaces/專題/feature-ab-test-v2/logs/ab_v2/`。

電腦硬碟一旦損壞，或 worktree 被清掉，報告裡的數字就無法追溯。

### 1.2 步驟

1. **把只存在 worktree 的結果收回 main**（`logs/` 不進 git，只是集中存放）：

   ```powershell
   $wt = "C:\Users\user\orca\workspaces\專題"
   Copy-Item -Recurse "$wt\feature-ab-test-v2\logs\ab_v2" "C:\Users\user\專題\logs\ab_v2"
   ```

   複製前先逐一檢查每個 worktree 的 `logs/`，確認 main 是否已有相同檔案：

   ```powershell
   git -C C:\Users\user\專題 worktree list
   Get-ChildItem "$wt\*\logs" -Directory | ForEach-Object { $_.FullName; Get-ChildItem $_ | Select-Object -ExpandProperty Name }
   ```

   總報告第八節中指向 worktree 路徑的項目，收回後改寫成 main 的路徑（見工作 2）。

2. **建立遠端 repo（需要你決定）**：
   - 建議建一個 **private** 的 GitHub repo，再 `git remote add origin <網址>`，然後 `git push -u origin main`。
   - push 前確認沒有任何 API key 或密碼：README 的安全說明寫明本專案不保存 key。先執行 `git grep -n -i "api_key\|secret\|password"` 檢查。
   - 要不要把其他 branch 一起 push，由你決定；main 已經包含所有合併後的成果。

3. **備份不進 git 的資料**：把下列資料夾壓縮後放到雲端硬碟或外接硬碟，**至少兩個地方**：

   | 資料夾 | 大小（約） | 內容 | 必要性 |
   |---|---|---|---|
   | `logs/` | 142 MB | 所有實驗結果 JSON、逐列預測、驗證紀錄 | **必要** |
   | `models/` | 34 MB | 模型、凍結模型與 `frozen_manifest.json` | **必要**（凍結模型是工作 8 的依據） |
   | `data/features/` | 見實際大小 | 所有實驗的輸入特徵檔 | **必要**（重現實驗需要） |
   | `data/raw/`、`data/processed/` | 見實際大小 | 原始與補值後 K 線 | 建議（可重新下載，但 Binance 未來可能修正歷史資料） |
   | `data/live/` | 見實際大小 | 即時更新的資料 | 可選（工作 8 時可重新抓） |

4. **寫一份備份清單** `backup_manifest.json`（跟備份檔放在一起，不進 git），列出每個檔案的路徑、大小與 SHA-256。之後要確認備份是否完整，只要重算 SHA-256 比對即可：

   ```powershell
   Get-ChildItem logs, models, data\features -Recurse -File |
     ForEach-Object { [pscustomobject]@{ path = $_.FullName.Replace("C:\Users\user\專題\", ""); bytes = $_.Length; sha256 = (Get-FileHash $_.FullName -Algorithm SHA256).Hash } } |
     ConvertTo-Json | Out-File backup_manifest.json -Encoding utf8
   ```

5. **（備份完成後才做）清理 worktree 與 branch**：已合併回 main 的 branch 可以刪除（`git branch -d`，小寫 d，未合併的會被拒絕）；worktree 用 `git worktree remove`。**每個 worktree 的 logs 確認已收回 main 並備份後，才能移除。**

### 1.3 完成條件

- [ ] 所有 worktree 中只存在一份的結果，都已收回 main 的 `logs/`。
- [ ] 遠端 repo 已建立並 push（或你決定不建立，並記錄原因）。
- [ ] `logs/`、`models/`、`data/features/` 至少備份在兩個地方。
- [ ] 從備份中隨機抽 3 個檔案，SHA-256 與 `backup_manifest.json` 相同。

| F9 | 三段式：交易比例 q 對每筆淨報酬（T、B、P 三條線） | `logs/three_class_target/multi_asset_three_class_target.json`（coverage_curve） | 所有 q 下都低於 0，三段式沒有明顯比較好 | 第 4 章 |

## 工作 4：專題報告撰寫

### 4.1 寫作原則

1. **誠實呈現弱訊號與負結果。**README 已規定：引用結果時使用 README「目前結果」表格的數字，不得以其他章節的較好數字替代。
2. **用詞一致**：
   - 未通過判定的，寫「沒有證據顯示……能改善」，不寫「沒有用」或「無效」。
   - 通過訊號關卡但未通過比較關卡的，寫「統計上有微弱訊號，但不足以……」。
   - 不寫「準確率高達」「可獲利」「可用於交易」。
3. **每個數字都能追溯**：報告中的數字來自結果文件或 `docs/figures/figure_data.json`，並在附錄列出對應的 JSON 檔。
4. **區分三種結果**：統計上顯著、描述性觀察（不參與判定）、事後觀察（例如 best-direction persistence，只能當上限參考）。
5. **BTC「定案 Transformer」的處理**：`時程.md` 記錄 BTC 在 08-19 選定 Transformer。報告中說明這是早期依三 fold 平均 AUC 最高所做的選擇；後續更嚴格的比較顯示，三模型差距在雜訊範圍內，因此整體結論是「沒有可靠的優勝模型」。不要刪掉這段歷史，也不要讓它看起來像結論。

### 4.2 章節架構與內容來源

**摘要（約 300～500 字）**
- 研究問題：用 5 年 1 小時 K 線預測四種主流幣未來 4 小時漲跌。
- 方法：53 個 K 線衍生特徵；XGBoost／LSTM／Transformer；expanding walk-forward 加 24 列 purge；預先登記的判定規則；block bootstrap 與 Holm 校正。
- 主要結果：AUC 約 0.50～0.53；外部特徵、特徵消融、多視窗、重訓頻率、三段式目標都沒有穩定改善；扣手續費後每筆淨報酬為負。
- 結論：訊號統計上存在但經濟上不足；嚴格評估的重要性。

**第 1 章 緒論**
- 研究動機：加密貨幣市場的高波動與預測需求。
- 研究問題：「在嚴格防止資料洩漏的條件下，K 線資料對未來漲跌方向有多少可預測性？」
- 研究範圍：依 `agement.md`，只做四種熱門幣的價格預測，不含穩定幣脫鉤預警（列為未來規劃）。
- 貢獻：
  1. 一套可重現的五年資料流程。
  2. 一套防洩漏、預先登記的評估框架。
  3. 一組可信的負結果，並分析原因。

**第 2 章 文獻探討**
- 效率市場假說與加密貨幣市場效率的相關研究。
- 機器學習與深度學習用於價格方向預測的研究，以及常見的資料洩漏問題（未來資料洩漏、隨機切分、在 test 上調門檻）。
- 時間序列交叉驗證：walk-forward、purge／embargo 的概念。
- 多重比較與可重現性問題（預先登記的意義）。
- 資料來源：若使用網路資料，每筆都附出處。

**第 3 章 資料與方法**

**第 5 章 討論：為什麼訊號這麼弱**
- 5.1 瓶頸在資料資訊量，不在模型：模型之間、特徵組合之間都收斂到同一個 AUC 上限。
- 5.2 可能原因：市場效率；53 個特徵都來自同一組 OHLCV，資訊高度重疊；外部資料是日頻，對 4h 預測太慢；小幅波動的標籤接近雜訊（BTC 約 28% 的 4h 波動在 ±0.2% 內）；市場規律會隨時間改變（F6、F8）。
- 5.3 統計訊號 vs 經濟價值：手續費損益兩平分析（F10）。
- 5.4 排除的解釋：程式錯誤（驗證 V1～V8、勘誤）、資料洩漏、模型能力、重訓頻率。
- 5.5 嚴格評估的意義：為什麼寬鬆評估（隨機切分、在 test 上調門檻）容易高估結果。本研究前一階段曾以 3 年資料做初步測試；本專案與報告僅使用 5 年資料與嚴格評估流程。

**第 6 章 結論與未來工作**
- 結論三點：訊號存在但弱；各種調整都沒有穩定改善；扣成本後不具交易價值。
- 研究限制：
  - test 期間在多個實驗中重複使用，不是獨立確認。
  - 只用現貨 K 線與日頻外部資料。
  - 只有固定手續費，沒有滑價。
  - 4h 標籤逐小時重疊。
  - `data/features` 由較舊版特徵程式產生（零成交量補值列的處理不同，影響約 40 列，都在 2021～2023 年）。
- 未來工作：
  1. 新資料獨立驗證（2027-01-25 之後，工作 8）。
  2. 換問題：預測波動大小，對應計畫書的風險預警方向。
  3. 換資訊來源：訂單簿、幣種間領先落後關係。
  4. 穩定幣脫鉤預警（計畫書原構想）。
